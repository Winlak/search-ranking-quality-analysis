# Сравнение качества поискового ранжирования

Портфолио-кейс продуктового аналитика о выборе между baseline и candidate-ranker. Все данные синтетические и воспроизводимо генерируются из кода; это не данные Яндекса или другой реальной компании.

## Бизнес-вопрос

Достаточно ли роста средней offline-метрики для выбора варианта выдачи, если часть запросов ухудшается?

Кейс рассчитывает NDCG@10, MRR@10, Success@3 и zero-relevant@10, использует парное сравнение на уровне запроса и отдельно проверяет platform × intent × translit. Итоговый вывод строится из фактического результата pipeline в [аналитическом отчёте](reports/analysis_report.md).

Сравнивается **перестановка фиксированного пула из 10 документов**, а не извлечение новых документов или обученная ML-модель. Оба варианта используют одинаковые `doc_id`, неизменные оценки релевантности и общий IDCG. Генератор намеренно задаёт локальное ухудшение; обнаружение этого среза проверяет метод, но не доказывает качество реального поиска.

SQL выполняется в DuckDB, а не только хранится для примера. Для всех 24 000 пар query/ranker сверяются NDCG, MRR и Success; допуск — 1e-12. [Результат сверки](outputs/validation.json). Срезы исследовательские, вывод о продакшен-запуске из синтетической симуляции не делается.

## Структура

```text
src/pipeline.py          генерация, метрики, срезы и отчёт
sql/ranking_metrics.sql SQL-расчёт метрик на уровне запроса
tests/                   unit-тесты формул
outputs/metrics.json     итоговые числа и худшие срезы
reports/                 decision-ready вывод
data/README.md           гранулярность и происхождение данных
```

## Запуск

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pytest -q
python -m src.pipeline
```

## Для резюме

На 12 000 синтетических запросов сравнил две перестановки одного пула документов: реализовал NDCG@10, MRR@10 и Success@3 в Python и SQL с поэлементной сверкой, построил парный доверительный интервал и показал, как средняя метрика скрывает ухудшение отдельного сегмента.
